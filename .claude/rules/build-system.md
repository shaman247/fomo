# Build System Details

## City config injection

`build.js` reads `config/<FOMO_CITY>.yaml` (`process.env.FOMO_CITY || 'nyc'`, parsed with the `yaml` devDep) and injects its `frontend:` block at build time:

- **Runtime JS** — a `;window.__CITY__ = {map, timezone};` prelude is **prepended** to the concatenated bundle (before flatpickr) so the global exists before any IIFE evaluates. `src/js/script.js` (`App.config` map fields) and `src/js/core/utils.js` (timezone) read it.
- **Branding** — `applyBranding()` replaces `{{SITE_NAME}}`, `{{DOMAIN}}`, `{{EMOJI}}`, `{{WELCOME_MODAL}}` tokens in `src/index.html` (runs last; the build **fails** on any leftover `{{TOKEN}}`). `src/about.html` is copied as-is (not tokenized).
- Dev watch includes `config/<FOMO_CITY>.yaml`, so config edits rebuild.

## JS Build

- JS modules use IIFE pattern with globals — they are **concatenated** (not bundled) then minified via `esbuild.transform()`. esbuild's bundler mode would break global scope.
- `build.js` reads `src/index.html` to determine JS file order — no separate manifest
- flatpickr installed via npm, prepended to JS/CSS bundles; the `window.__CITY__` prelude sits before flatpickr

## CSS Build

- CSS `@import` chain resolved and minified via `esbuild.build()` with `bundle: true`
- Font path rewrite: `../fonts/` → `fonts/` (CSS moves from subdir to root in bundle)
- Font URL versioning: `versionedFontUrl()` appends `?v=<md5(content)>` to every `fonts/*.woff2|ttf` URL in the CSS bundle AND to the font entries in the SW precache manifest (same helper, always in sync). Font filenames are stable but 1-year-cached and SW-precached as immutable — without the version query, changed font bytes (e.g. re-frozen OpenType features via `scripts/freeze_inter_features.py`) would never reach returning visitors.

## Dev vs Prod

- Dev (`npm run dev`): unminified, stable filenames, symlinks `data/`, `images/`, `fonts/`, `api/`, `admin/`, `vendor/` from `dist/` → `src/`
- Prod (`npm run build`): minified, content-hashed filenames, copies those directories into `dist/`

## Generated-data fallback

`src/data/tag_hierarchy.json` is regenerated by every pipeline run, so it's **gitignored**. A committed `src/data/tag_hierarchy.example.json` is the fallback. `build.js` (`EXAMPLE_DATA_FILES` → `ensureSeededData()`) copies the example to the live filename **only if the live file is absent** (fresh checkout / fork with no pipeline export yet) — a real export always wins. `*.example.json` files are skipped when copying into `dist/`, so they never ship. To refresh the fallback, copy the current live file over the example and commit it.

## Deployment

```bash
npm run build                          # Build to dist/
python scripts/upload_public_html.py   # Upload dist/ to server via FTP
```

The upload script tracks file content hashes (MD5) in `scripts/upload_state.json` and only uploads changed files. Use `--force` to upload everything.

**Frontend gate**: when the app bundle changed since the last upload (a new `app.<hash>.js` name, or a different `index.html` hash), the upload first runs `npm test` (every `src/js/tests/*.test.cjs`) and `scripts/frontend_smoke.py` (headless Chromium over DPR 0.9–2, three device timezones and a mobile viewport: fails on any page/console error, blank map sprites, event times that differ from a New-York-device run, or a missing ErrorReporter beacon) and uploads nothing if either fails. Data-only uploads skip it. `--skip-frontend-checks` overrides. Run the smoke alone with `./venv/bin/python scripts/frontend_smoke.py [--dist DIR] [--only dpr-1.25,tz-london]`.

**Client error reporting**: `src/js/core/errorReporter.js` (after `beacon.js`, the shared device-context/sendBeacon helper both beacons use) beacons uncaught errors, unhandled rejections and `console.error` calls (max 5 per page load, deduped per session, URLs cut to file names) to `api/client_errors.php`, which appends to a log outside the web root. Summarize with `./venv/bin/python scripts/client_errors.py [--days N] [--bundle HASH]`. It shows only new or recurred error signatures, which stay stable across deploys. Record verdicts with `--mark SIG --verdict ignored|backlog|fixed --note …`, stored in the local `.claude/client-error-triage.json`, and use `--show SIG` to inspect one. A weekly review procedure is in `.claude/recurring-checks.md` ("Weekly: Review client error reports").

**Analytics**: `src/js/core/analytics.js` sends a `view` beacon on load and an `engage` beacon (visible seconds, feature-use counts from delegated DOM listeners, first-use flags) each time the page is hidden. It runs only on `frontend.domain` (never in dev or the smoke test) and is off under Do Not Track/GPC. `api/analytics.php` (shared helpers in `api/beacon_lib.php`) only adds to daily counter files in `<parent of DOCUMENT_ROOT>/analytics/YYYY-MM-DD.json`, in city-timezone days. No per-visit rows, no IPs, no visitor counting (a deliberate choice, disclosed in `privacy.html`). The native apps are reported as `ios-app`/`android-app` through `frontend.native_app_ua`. To add a tracked action, add it to `CLICKS`/`CHANGES` in analytics.js, `ACTIONS` in analytics.php and `ACTIONS` in `scripts/analytics_report.py`. Report: `./venv/bin/python scripts/analytics_report.py [--days N] [--html] [--note TEXT]`. `--html` writes the local, gitignored dashboard page `.claude/analytics-dashboard.html` (inline CSS/SVG, no network), and `--note` adds dated review notes to it. A weekly review updates it (`.claude/recurring-checks.md`, "Weekly: Review analytics and update the dashboard"). It never uploads `dist/data/similarity/`: a similarity model generation goes live only through the gated `pipeline/similarity_publish.py` (procedure in `pipeline/similarity.md`).

## Service worker emission

`build.js` `emitServiceWorker()` renders `src/sw.js` (a template — never served as-is) into `dist/sw.js`, injecting the precache manifest (hashed bundles + versioned vendor + fonts + map styles) and a version hash so any shell change reinstalls the precache. Data JSONs are deliberately NOT SW-cached — the page owns them in IndexedDB (`src/js/data/dataCache.js`). Controls:

- **Dev builds and `frontend.sw_enabled: false`** emit a self-unregistering "killer" sw.js (activate → wipe all SW caches + unregister; IndexedDB untouched) and set `window.__CITY__.swEnabled = false` so the page doesn't register. This is also the production rollback path — deploy a disabled build's sw.js, no app-store release needed.
- `src/.htaccess` serves `sw.js` with `Cache-Control: no-cache` (mandatory — the blanket 1-year JS rule would otherwise freeze SW updates).
- `sw.js` sits at the dist root; the index.html JS-concat regex only matches `js/…` paths, so it never joins the app bundle.
